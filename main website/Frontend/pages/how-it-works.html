How ZdexCloud Turns an Android Phone Into a Remote File Server

From local Android flash storage to an authorized remote web browser, follow the complete connection and data-access path across firewalls and cellular networks.

Onboarding Sequence

The Five-Stage User Journey

A step-by-step walkthrough of what happens, why it is necessary, and what you see during setup.

01

Stage 1: Create a ZdexCloud Account

What happens: You register your account at zdexcloud.com using your email and verify your identity via a 2FA one-time password (OTP).

Why it is necessary: The control plane establishes your identity, assigns your secure user workspace, and authorizes device registrations.

What you see: Registration form, 6-digit OTP verification screen, and welcome dashboard.
02

Stage 2: Install and Sign In to the Android App

What happens: You install the ZdexCloud APK on your dedicated Android phone (Android 8.0+) and sign in using your account credentials.

Why it is necessary: The phone establishes a cryptographic hardware binding by generating a persistent installationId in Android Keystore and registers itself as one of your up to 5 allowed servers.

What you see: Android login screen followed by the device setup and server configuration screen.
03

Stage 3: Configure Server & Grant Permissions

What happens: You name your server (e.g., "Home Vault"), set a dedicated server access password, and grant Android storage access.

Why it is necessary: Android requires explicit user permission to read internal flash storage and micro-SD cards. The dedicated server password decouples file access from your web account credentials.

What you see: Android system storage permission prompt and server credential fields.
04

Stage 4: Start the Server Host Engine

What happens: You tap "Start Server". The Android Foreground Service initializes the local HTTP engine bound to loopback and initiates an outbound encrypted WebSocket connection over TLS 1.3 to the ZdexCloud connection gateway.

Why it is necessary: The foreground service ensures the Android OS does not sleep the server, and the outbound WebSocket bridges your phone to the gateway without router port forwarding.

What you see: Server state turns "RUNNING" and a persistent Android system notification appears.
05

Stage 5: Access Files Remotely in Any Web Browser

What happens: From any computer, tablet, or phone, you log in to zdexcloud.com, select your active server, enter its server password, and open the web file manager.

Why it is necessary: File directory listings, uploads, downloads, and streaming playback are tunneled through the gateway directly to your phone's storage.

What you see: Full-featured desktop-grade file manager with folder trees, photos, and video players.
Deep Architecture

The Technical Connection Sequence

A comprehensive layer-by-layer breakdown of how messages and data travel across the system.

1. User Web Browser

You sign in to zdexcloud.com. The browser establishes an HTTPS/WSS session with the platform control plane and receives authenticated session cookies with strict 24-hour expiry.

2. ZdexCloud Control Plane

Verifies account identity, confirms active device registration, checks gateway presence status, and issues connection authorization tickets. Zero file bytes pass through or reside in the control plane database.

3. ZdexCloud Relay Gateway

A high-throughput, stateless routing node. It holds active WebSocket connections in memory and routes RPC messages and binary streaming chunks between the browser and phone sockets. The gateway writes 0 bytes to disk.

4. Outbound TLS 1.3 Connection

The Android phone initiated this persistent connection out through port 443. All firewalls, home routers, and cellular carrier networks permit this outbound client socket without manual forwarding rules.

5. Android Server Engine & Loopback Interface

An internal bridge forwards RPC messages into the phone's internal HTTP engine bound strictly to the local loopback interface. This engine is isolated from your local Wi-Fi LAN to prevent unauthorized local access.

6. Physical Storage Host (Phone Flash & Micro-SD)

The phone reads file data from internal storage (/storage/emulated/0) or an inserted micro-SD card and sends data chunks back up through the outbound socket to your browser.

Networking Reality

Why Outbound Connections Matter: Bypassing CGNAT

Traditional self-hosting requires opening your home router. ZdexCloud eliminates that entire layer of friction.

The Traditional Inbound Model

Traditional home servers (like Raspberry Pi, TrueNAS, or Apache) wait for external clients to initiate connections inbound into your home network:

  • Requires accessing router admin settings to configure port forwarding (ports 80, 443, 22).
  • Requires a dedicated, public IPv4 address or dynamic DNS (DDNS) daemon.
  • Completely blocked by Carrier-Grade NAT (CGNAT): Cellular mobile networks and modern fiber ISPs share one public IP among thousands of customers; inbound ports cannot reach your home router.
  • Exposes your local router to continuous scanning by malicious bots on the public internet.

ZdexCloud's Outbound Model

ZdexCloud relies entirely on an outbound client connection initiated by the Android phone:

  • The phone connects outbound over standard HTTPS/WSS port 443, exactly like a browser opening a web page.
  • Because all consumer routers, NAT devices, and mobile carriers allow outbound connections, the tunnel establishes instantly.
  • Carrier-Grade NAT (CGNAT) Compatible: Functions seamlessly behind 4G/5G mobile carriers, apartment Wi-Fi, university dorm networks, and residential fiber.
  • Zero Open Ports: Your home router exposes no listening ports to the outside world.

Direct AEO Answer: Can ZdexCloud work behind CGNAT? Yes. Carrier-Grade NAT (CGNAT) only restricts inbound connection requests from the public internet. Because ZdexCloud uses an outbound-only connection model where the Android smartphone initiates the connection out to the relay gateway over standard TLS 1.3 (port 443), it operates reliably across CGNAT, residential fiber, and mobile hotspot networks without router port forwarding.

Operational Transparency

Where Files Move: The Four Operational Flows

A clear explanation of how data travels during download, upload, streaming, and folder management.

1. Download Flow

Browser clicks download on a file:

  1. Browser sends authenticated DOWNLOAD request with file path to the gateway.
  2. Gateway routes the request packet to your phone's active socket.
  3. Android app reads binary file chunks from flash/SD storage.
  4. Chunks stream across the TLS 1.3 tunnel through relay memory to the browser.
  5. Browser compiles the stream and saves the file to your local computer.

2. Upload Flow

Browser drops a file into the upload zone:

  1. Browser slices file into binary chunks and sends an UPLOAD stream to gateway.
  2. Gateway forwards data packets in RAM directly to the target Android phone.
  3. Internal bridge transfers payload to the local loopback HTTP engine.
  4. Android server engine writes chunks directly to phone flash storage or micro-SD.
  5. Phone confirms successful write; browser updates file list immediately.

3. Media Streaming Flow

User clicks a video or photo thumbnail:

  1. Browser initiates byte-range HTTP request via gateway tunnel.
  2. Android server reads corresponding byte offset from phone storage.
  3. Data is streamed in real time without buffering the entire multi-gigabyte file.
  4. Browser video player renders playback with instant seek capabilities.

4. Folder & Organization Operations

User creates a folder, renames, or deletes an item:

  1. Browser sends JSON RPC command (CREATE_FOLDER, RENAME, or DELETE).
  2. Gateway checks authentication and idempotency cache before forwarding.
  3. Phone filesystem executes native file operation.
  4. Phone returns success response and browser refreshes directory view.

Essential Privacy Distinction: Storage Location vs. Transport Path

We never claim that "files never leave your phone," because remote downloading and media streaming inherently require file data to travel across the network. The key distinction is that storage is hosted directly on your phone (personal files are not permanently stored on cloud disks), while transport occurs in-flight over encrypted TLS 1.3 connections only when an active operation is requested.

Process Management

Server Lifecycle & Android Background Execution

Understanding the state machine that keeps your phone server operating unattended.

Server State Machine

The engine transitions predictably through distinct states:

  • STOPPED: Engine idle; 0 power drawn.
  • CONNECTING: Initializing loopback server and reaching gateway.
  • CONNECTED / RUNNING: Gateway tunnel verified; ready for remote requests.
  • RECONNECTING: Wi-Fi dropped; backoff retry active.

Foreground Service & Notification

Android OS aggressively terminates idle background tasks. ZdexCloud runs as an official Android Foreground Service with a persistent system status notification, declaring to Android that the server process is critical and must not be killed.

Battery Optimization (Doze Mode)

Android Doze suspends network activity when a device is stationary. To ensure 24/7 remote availability, you must whitelist ZdexCloud under Settings > Battery > Unrestricted / Do Not Optimize.

Android OEM Task Killer Variations

Certain phone manufacturers (such as Xiaomi MIUI/HyperOS, Samsung OneUI, and Huawei EMUI) incorporate proprietary battery managers that terminate background apps despite standard permissions. If your server disconnects after screen lock, check manufacturer settings to enable "Autostart" and lock the app in the Recent Apps overview.

Fleet Scaling

Multi-Server Architecture: Up to 5 Phones

How a single user account coordinates multiple physical Android servers across different networks.

Separate Physical Server Identities

You are not limited to a single phone. Each physical device generates its own hardware-bound identity during setup:

  • Persistent Identity: Each phone maintains a cryptographically generated installationId.
  • Independent Network Locations: Servers can reside on different Wi-Fi networks in different cities (e.g. Home, Office, Family Studio).
  • Decoupled Passwords: Each phone server can have its own distinct access password for compartmentalized security.

Capacity Limits & 1-Click Switching

Manage your personal server fleet from a unified dashboard:

  • Strict 5-Device Cap: You can register up to 5 physical phone servers per account. We do not make false claims of "unlimited servers".
  • 1-Click Switching: Switch between online servers from the dropdown menu in the web file manager without logging out.
  • Independent Storage Metrics: Monitor individual storage capacity and remaining free space for each server separately.
